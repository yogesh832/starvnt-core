STARVNT Notification System

Production-Grade, Context-Aware & Non-Spam Notification Architecture

1. Objective

Build a centralized, event-driven Notification Service for STARVNT that communicates with Customers, Vendors, and Admins only when a notification provides genuine value.

The system must feel:

- Personal
- Relevant
- Timely
- Human
- Trustworthy
- Context-aware
- Action-oriented

It must NOT feel like an automated spam system.

Core Principle

«Notify only when there is a meaningful reason to notify.»

Every notification must answer at least one of these questions:

1. What changed?
2. What does the user need to know?
3. What action is required?
4. What important milestone has been reached?
5. What risk or deadline should the user be aware of?

If none apply, do not send the notification.

---

2. Notification Channels

The Notification Service should support:

- In-App Notification
- Push Notification
- WhatsApp

- Email

Channels must be provider-independent.

Example:

      ↓

      ↓

      ↓

The system must allow STARVNT to change providers without changing the core business logic.

3. Notification Philosophy

3.1 Transactional First

The primary purpose of notifications is to support the customer's event journey.

Examples:

- OTP
- Booking confirmation
- Payment confirmation
- Quotation availability
- Important event update
- Vendor assignment
- Deadline reminder
- Cancellation/refund

Marketing notifications must remain a separate system.

---

3.2 No Duplicate Communication

If the same information has already been successfully communicated through an appropriate channel, do not unnecessarily send the same information through multiple channels.

Example:

BAD:

Booking confirmed
→ SMS
→ WhatsApp
→ Email
→ Push
→ 4 separate notifications

BETTER:

Booking confirmed
→ In-App + Push

SMS only if required or configured.
Email for the official booking record.

The channel strategy must depend on:

- Urgency
- User preference
- Message importance
- Previous delivery status
- Regulatory requirements

31. Acceptance Criteria

The system will be considered production-ready only when:

- No duplicate notification is generated for the same event.
- Notifications are triggered from business events rather than scattered throughout the codebase.
- Failed notifications can be retried safely.
- Delivery status is tracked.
- Provider APIs can be replaced without rewriting STARVNT Core.
- Marketing and transactional communication are completely separated.
- User preferences are respected where applicable.
- Notification frequency can be controlled.
- Every notification has a clear business reason.
- Customer-facing messages do not expose unnecessary internal system information.
- Notification content is concise, natural and context-aware.
- The system does not send notifications merely because an internal database field changed.
- Critical notifications cannot be silently lost.
- Notification delivery failure does not break booking/payment/event operations.

If a vendor is 60 km away but has configured a 50 km service radius, the system should not automatically treat them as normally eligible. However, if there are no valid vendors within the standard service area, we should support an Out-of-Coverage / Extended Service Option state.
Flow:
1. Standard Matching:
First check vendors strictly against their configured service coverage/radius.
2. If valid vendors exist:
Show only normally eligible vendors.
3. If no valid vendors exist:
Search a broader fallback range, but do not silently override the vendor's 50 km limit.
4. If an out-of-radius vendor is technically capable:
Show it separately as: “Extended Service — 60 km away”
with clear indication that additional travel/logistics charges may apply and vendor confirmation is required.
5. Vendor must explicitly accept the extended-distance requirement before it becomes a valid option/quote.
So the rule is:
Eligibility ≠ Proximity.
Configured coverage is the normal eligibility rule.
Out-of-radius vendors can be surfaced only as a clearly labelled fallback opportunity, never silently converted into eligible vendors.
Also, the fallback should go through coverage → availability → capacity → operational feasibility → travel/logistics → validated total cost → vendor confirmation.
Customer should never see a vendor as “available” when the vendor has not actually confirmed that they can serve that location.
This keeps the Core truth intact while preventing a dead-end “No Results” experience when a potentially usable vendor exists.

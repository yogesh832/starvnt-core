# Vendor dashboard metric definitions

This register documents the Vendor Dashboard sales widget implemented in `web/src/pages/vendor/dashboardMetrics.js`. It intentionally describes the supported slice, not unimplemented KPI cards elsewhere in the master specification.

| Metric | Source and join | Calculation / eligibility | Period and exclusions | Drill-down |
| --- | --- | --- | --- | --- |
| Eligible enquiries | Vendor-owned `Opportunity` rows; record key `_id`, timestamp `createdAt`. | Count unique enquiries with valid creation timestamps in the selected cohort period. | UTC rolling interval ending 30 days before the calculation time; 30/60/90 days long. Invalid/missing timestamps are excluded. The last 30 days are excluded to allow the attribution window to mature. | `/vendor/enquiries` |
| Enquiries with submitted quote | Vendor-owned `Quote` rows joined by `Quote.opportunity` to an eligible enquiry. | Count unique enquiries having at least one recorded first `history.toStatus=SUBMITTED` timestamp no later than 30 days after that enquiry. Multiple quotes for one enquiry count once. | Current quote status does not erase a historical submission. Drafts and legacy quotes without a recorded submission transition do not qualify. | `/vendor/quotes` |
| Enquiry-to-quote rate | The two metrics above. | Unique eligible enquiries with a qualifying quote ÷ eligible enquiries. | If denominator is zero, show “Insufficient data.” Rate is rounded to a whole percent in the UI. | `/vendor/quotes` |
| Confirmed bookings | Vendor-owned `CoreBooking` rows joined by `CoreBooking.opportunityId` to an eligible enquiry. | Count unique enquiries with a Core booking in `CONFIRMED` state created no later than 30 days after enquiry creation. Booking IDs are never inferred from quote totals. | Cancelled/failed bookings do not qualify; missing opportunity IDs or creation timestamps are excluded. Multiple confirmed records for one opportunity count once. | `/vendor/bookings` |
| Enquiry-to-confirmed-booking rate | Confirmed bookings and eligible enquiry count above. | Unique eligible enquiries with a linked Core-confirmed booking ÷ eligible enquiries. | Zero denominator yields “Insufficient data.” Quote approval alone is not a conversion. | `/vendor/bookings` |
| Average time to first submitted quote | Opportunity `createdAt`, linked Quote `opportunity`, and first Quote history transition to `SUBMITTED`. | Mean of the first recorded quote submission time minus enquiry creation time for eligible enquiries that received a qualifying quote within 30 days. UI also shows the sample count. | Quotes lacking submission history or linkage are excluded; no samples yields “Insufficient data.” This is quote turnaround, not a complete measure of all message responses. | `/vendor/quotes` |
| Declined enquiries with recorded reasons | Vendor-owned `Opportunity` status and vendor-entered `declineReason`. | Count distinct declined enquiries with a non-empty saved reason in the selected mature cohort; show up to three exact reason strings and counts. | New declines require an internal vendor reason. Legacy declines without a reason are excluded; text is not sent to the customer. | `/vendor/enquiries` |
| Average first vendor response (quote or message) | Authenticated `/vendor/metrics/first-response`; vendor-owned Opportunities, Quote submission history, and VendorMessageThread vendor messages. Threads link by `opportunity` or by a quote linked to that opportunity. Existing `slaResponseTimeMs` is also accepted when present. | For each unique enquiry, use the earliest recorded vendor message or submitted quote after enquiry creation; average only enquiries with a response and display responded sample count over eligible enquiries. No PII or message text is returned by the endpoint. | Matured rolling UTC enquiry cohort: selected 30/60/90 days ending 30 days before calculation time. Data is marked incomplete and the average omitted if bounded query limits are reached. No samples yields “Insufficient data.” | `/vendor/messages` or `/vendor/quotes` |
| Verified advance received (dashboard KPI) | Vendor `CoreBooking.paymentSummary.paidAmount`, `paymentStatus`, `bookingStatus`. | Sum paid amount only for Core-confirmed bookings whose payment status is `PAYMENT_VERIFIED`. | All time; no payment initiation, pending or unverified amount is counted. This is distinct from gross booking value and settlements. A failed booking API shows unavailable. | `/vendor/payments` |
| Outstanding customer balance (dashboard finance summary) | `/vendor/financial-truth` → `metrics.expectedReceivables`. | Display the existing Core financial-truth calculation for unpaid contract amounts on confirmed vendor bookings. | All time; this is customer receivables, not vendor earnings. API failure is displayed as unavailable. | `/vendor/payments` |
| Overdue customer balance (dashboard finance summary) | `/vendor/financial-truth` → `metrics.overdueAmount`. | Display the existing Core financial-truth overdue balance. | All time; follow the existing Core due-date and payment reconciliation rules. API failure is displayed as unavailable. | `/vendor/payments` |
| Customer balance due this week (dashboard finance summary) | `/vendor/financial-truth` → `metrics.dueThisWeek`. | Display Core's unpaid confirmed-booking receivables whose existing due-date rule places them within the next seven days. | All time; this is customer receivable, not vendor earnings. API failure is unavailable. | `/vendor/payments` |
| Settlement eligible (dashboard finance summary) | `/vendor/financial-truth` → `metrics.expectedSettlements`. | Sum vendor payable only when the Core booking state is `SETTLEMENT_ELIGIBLE`. Completion verification alone and payout-review delay do not qualify. | All time; not equivalent to initiated or completed settlement. | `/vendor/payments` |
| Settlement on hold (dashboard finance summary) | `/vendor/financial-truth` → `metrics.settlementHoldAmount`. | Sum vendor payable for confirmed bookings in Core state `SETTLEMENT_HOLD`. | All time; holds are excluded from settlement-eligible and settled totals. | `/vendor/payments` |
| Vendor settlements completed (dashboard finance summary) | `/vendor/financial-truth` → `metrics.settledAmount`. | Display vendor payable for Core bookings whose settlement state is `SETTLED`. | All time; eligibility and payment initiation are not counted as completed. API failure is displayed as unavailable. | `/vendor/payments` |
| Goal: submitted quotes | Vendor `Quote` rows and status history. | Count quotes with a recorded `SUBMITTED` transition in the configured period, even if they later move to another state. | Period start/end are UTC date boundaries; end date is inclusive in the vendor form. Missing submission history is excluded. | `/vendor/quotes` |
| Weekly counts | Existing vendor-scoped enquiries, quote history, Core bookings and published reviews. | Counts events in the elapsed current UTC calendar week and compares with the same elapsed portion of the prior UTC week. | Failed sources mark the section unavailable. Zero prior-period values do not produce a percentage-growth claim. Response and task-completion totals are excluded because no reliable shared source is available. | Existing `/vendor/enquiries`, `/vendor/quotes`, `/vendor/bookings`, `/vendor/reviews` modules |
| Goal: confirmed bookings | Vendor `CoreBooking` rows. | Count bookings with `bookingStatus=CONFIRMED` and `createdAt` in the configured period. | Period is vendor-configured (maximum 366 days); failed/cancelled bookings are excluded. | `/vendor/bookings` |
| Goal: completed bookings | Vendor `CoreBooking` rows. | Count bookings with `executionStatus=COMPLETION_VERIFIED` and Core `validationAudit.verifiedAt` in the configured period. | Completion claims submitted by vendors are not counted until Core verification is recorded. | `/vendor/bookings` |

## Boundaries and caveats

- Cohort date arithmetic uses UTC timestamps. Business-local calendar reporting needs an explicit product timezone contract before server-side rollups are introduced.
- The current widget reads existing vendor-scoped API records and computes the selected cohort in the web client. It does not add a new endpoint, database aggregation, cache, or persisted snapshot.
- The eligible cohort is based on enquiry receipt date, and conversions are attributed for 30 days after each enquiry. This transparent policy is a reporting convention in this code slice; it is not a newly introduced booking lifecycle rule.
- Conversion is not fully reliable for historical records without opportunity links, timestamps or quote submission history. Those records are excluded, not guessed.
- The goal panel currently supports only the three count metrics above. It does not offer a response-time goal because goal direction/target units and baseline rules are not yet defined. The dashboard does not calculate qualified enquiries, lost-reason rates, profit, or percentage weekly growth. Their underlying definitions or sources need further audit before display.
- The current Core booking model does not represent a separate settlement-initiated status; the dashboard does not fabricate one. Refunds/adjustments and authorized dispute balances are not derived from an authoritative vendor financial summary here.
